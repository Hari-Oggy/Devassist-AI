## ANALYSIS PHASE — DO THIS BEFORE WRITING A SINGLE DOCSTRING

Read the entire file top to bottom. Build a mental model before writing anything.

### Understand the module:
- What domain does this file operate in? (auth, data pipeline, API client, agent tool, RAG system, etc.)
- What is the primary responsibility of this module in one sentence?
- Are there existing docstrings? If yes — match their depth, tone, and style exactly.
- What are the key data structures flowing through this file? (Check type hints, return types, class attributes)

### For EACH undocumented item, determine before writing:
- What does this ACTUALLY do? Read every line of the implementation. Do not infer from the name.
- What are valid inputs? Are there constraints? (must be positive? non-empty? pre-initialized? a specific format?)
- What does it return? What does the return value MEAN in domain terms?
- Can it return None? Under what condition?
- What exceptions does it raise — explicitly (raise ...) or implicitly (from dependencies like open(), requests.get(), json.loads())?
- Does it have side effects? (modifies self, writes to disk, makes network calls, mutates input arguments)
- Is it called from anywhere visible in the file? That tells you the real usage contract.

## DOCSTRING QUALITY STANDARDS

### THE 4 CARDINAL RULES — VIOLATIONS ARE UNACCEPTABLE

RULE 1 — NEVER restate the function name as the summary
  BAD:  def get_user():      →  """Gets the user."""
  BAD:  def load_index():    →  """Loads the index."""
  BAD:  def build_index():   →  """Builds the index."""
  GOOD: def get_user():      →  """Fetches a single user record from the database by primary key."""
  GOOD: def load_index():    →  """Deserializes a persisted FAISS index from disk into memory for similarity search."""
  GOOD: def build_index():   →  """Chunks, embeds, and persists the entire codebase into a FAISS vector index."""

RULE 2 — NEVER use vague filler words: "handles", "processes", "deals with", "manages", "performs", "does"
  BAD:  """Handles the API response."""
  BAD:  """Processes the input data."""
  BAD:  """Manages the connection."""
  GOOD: """Parses a raw GitHub API response into a typed PullRequest object, raising ValueError if required fields are absent."""
  GOOD: """Validates, normalizes, and stores the incoming webhook payload to the events table."""
  GOOD: """Opens a persistent PostgreSQL connection pool and registers a shutdown hook to close it on exit."""

RULE 3 — NEVER document what is already obvious from the type hint alone
  BAD:  file_path (str): The file path string.
  BAD:  user_id (int): The user ID as an integer.
  BAD:  enabled (bool): Whether it is enabled.
  GOOD: file_path (str): Absolute path to the Python source file. Must exist and be readable; raises FileNotFoundError otherwise.
  GOOD: user_id (int): Primary key of the target user. Must be a positive integer; raises ValueError if <= 0.
  GOOD: enabled (bool): When True, sends results to GitHub as inline PR comments. When False, returns results only without posting.

RULE 4 — NEVER document a Raises section based on what COULD happen — only what the implementation ACTUALLY raises
  BAD:  Raises: Exception: If something goes wrong.
  BAD:  Raises: ValueError: If the input is invalid.  (without reading the code to confirm this)
  GOOD: Raises: FileNotFoundError: If index_path does not exist or was not created by build_index().
  GOOD: Raises: json.JSONDecodeError: If the linter output is not valid JSON, which occurs when pylint exits with a fatal error.
  GOOD: Raises: github.GithubException: If the PR number does not exist or the token lacks repo read permissions.

## GOOGLE-STYLE FORMAT — EXACT STRUCTURE

```python
def function_name(param1: type, param2: type, optional: type = default) -> ReturnType:
    """Imperative-mood summary. One sentence. No period unless followed by more text.

    Extended description ONLY if needed — explain the algorithm, non-obvious behavior,
    important preconditions, or WHY this exists. If the one-liner is complete, skip this.
    Keep it to 2-3 sentences maximum.

    Args:
        param1 (type): What it represents + any constraints or valid range.
        param2 (type): What it represents + what happens if it is None or empty.
        optional (type, optional): What it represents. Defaults to {default}.

    Returns:
        type: What the value represents in domain terms. If dict — name the keys.
              If the return can be None — say exactly when.

    Raises:
        SpecificException: Exact condition that triggers this. Read the code first.
        AnotherException: Only if the implementation actually raises it.

    Example:
        Include ONLY if usage is non-obvious or has tricky argument combinations.
        Must be real, runnable code — not pseudocode.

        >>> retriever = CodebaseRetriever("/path/to/index")
        >>> context = retriever.get_context("error handling patterns")
        >>> print(context[:200])
    """
```

## SPECIAL CASES — HANDLE EXACTLY AS SPECIFIED

`__init__` methods:
  Document on the CLASS docstring, not on __init__ itself.
  The Args section of the class docstring covers constructor parameters.
  Leave __init__ without its own docstring.

Private methods (single underscore _name):
  Document if the body is longer than 8 lines OR if it raises exceptions.
  Use abbreviated form: one-liner summary + Args only if parameters are non-obvious.
  Skip Returns section if it returns a primitive with an obvious meaning.

`__str__` and `__repr__`:
  One-liner only: """Returns a human-readable string for logging and debugging."""

Abstract methods:
  Document the CONTRACT that subclasses must fulfill — not a hypothetical implementation.
  GOOD: """Validates the payload. Subclasses must raise ValidationError on failure, never return False or None."""

Properties (@property):
  One-liner describing what it computes or exposes. Note caching or lazy evaluation if present.
  GOOD: """Returns True if the FAISS index is loaded into memory and ready for queries."""

Short dunder methods (__len__, __contains__, __iter__):
  One-liner only unless behavior is non-standard.
